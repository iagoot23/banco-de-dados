Como os dados eram guardados

Papel

Fichas e livros de registro: busca manual, cópias divergentes, risco de perda.

Acesso sequencial

Fitas magnéticas (décadas de 1950–60): para ler o registro 1000 é preciso passar pelos 999 anteriores.

Acesso direto

Discos rígidos (HD) e SSD: qualquer registro é lido diretamente, em milissegundos.

Como organizar os dados: os modelos

Ao longo da história surgiram formas diferentes de ligar os dados entre si. Cada forma é um modelo de banco de dados.

Hierárquico (1960)

Dados em árvore: cada registro tem um único “pai”.

Em rede (1960)

Dados em grafo: um registro pode ter vários “pais”.

Relacional (1970)

Dados em tabelas ligadas por chaves. É o padrão até hoje.

Modelo hierárquico

NívelExemplo
RaizEscola
FilhoTurma 3A, Turma 3B
NetoAlunos de cada turma
  • Navegação de cima para baixo, como pastas do Windows.
  • Ótimo para dados que são naturalmente uma árvore.
  • Problema: um aluno em duas turmas precisaria ser copiado.
  • Ainda existe no registro do Windows e em formatos como XML.

Modelo em rede

  • Cada registro aponta para outros por ligações (ponteiros).
  • Um aluno pode pertencer a várias turmas sem cópia.
  • Problema: o programa precisa conhecer o caminho das ligações para encontrar um dado.
  • Qualquer mudança na estrutura obriga a reescrever os programas.

Os dois modelos dos anos 1960 caíram em desuso: eram difíceis de mudar e de consultar.

Modelo relacional (Edgar F. Codd, 1970)

A ligação é pelo valor da chave: o programa só precisa perguntar o que quer, não por onde ir.

Por que o modelo relacional venceu

  • Tabelas são fáceis de entender: parecem planilhas.
  • Uma linguagem padrão, o SQL, para todas as operações.
  • A estrutura pode mudar sem reescrever os programas.
  • Regras de integridade garantem dados consistentes.
  • PostgreSQL, MySQL, SQL Server, Oracle e SQLite são todos relacionais.

Bancos não relacionais (NoSQL)

Documento

Guarda objetos JSON inteiros. Ex.: MongoDB. Bom para cadastros com campos variáveis.

Chave-valor

Uma chave aponta para um valor. Ex.: Redis. Muito rápido para sessões e cache.

Séries temporais

Leituras de sensores ao longo do tempo. Ex.: InfluxDB, TimescaleDB (dentro do PostgreSQL).

Grafo

Pessoas e ligações. Ex.: Neo4j. Bom para redes sociais e rotas.

Os modelos não relacionais voltam no dia 40, na prática.

Relacional ou não relacional?

CritérioRelacionalNão relacional
EstruturaFixa, definida antes (esquema)Flexível, pode variar por registro
ConsultasSQL padronizado, junções entre tabelasPróprias de cada produto
ConsistênciaForte (transações ACID)Muitas vezes eventual
Uso típicoEscola, banco, loja, ERPCache, logs, sensores, redes sociais

Na dúvida, o relacional é o ponto de partida: quase todo sistema começa nele.

Sistema Gerenciador de Banco de Dados (SGBD)

  • É o programa que cria, guarda e controla os bancos de dados.
  • Recebe os comandos SQL e devolve os resultados.
  • Ninguém abre o arquivo do banco diretamente: tudo passa pelo SGBD.
  • Exemplos: PostgreSQL, MySQL, SQL Server, SQLite.

Banco de dados = os dados. SGBD = o software que cuida deles.

O que um SGBD faz

Armazena

Organiza os dados em disco de forma eficiente e cria índices para buscas rápidas.

Controla acesso

Usuários, senhas e permissões por tabela.

Mantém a integridade

Recusa dados que violam as regras: chave repetida, campo obrigatório vazio.

Recupera falhas

Transações, registro de alterações (log) e cópias de segurança.

Todo sistema de cadastro, do mais simples ao mais complexo, é feito de CRUD.

Cliente e servidor

  • O servidor é o SGBD rodando em uma máquina, esperando conexões (no PostgreSQL, porta 5432).
  • O cliente é qualquer programa que se conecta e envia SQL: psql, DBeaver, um site, um aplicativo.
  • Vários clientes usam o mesmo servidor ao mesmo tempo.

Tipos de SGBD

Servidor

Um processo separado atende muitos clientes pela rede. PostgreSQL, MySQL, SQL Server, Oracle.

Embutido

O banco é uma biblioteca dentro do próprio programa, sem servidor. SQLite: celulares, navegadores, embarcados.

Em nuvem

O provedor administra o servidor. Supabase, Amazon RDS, Azure SQL.

A linguagem SQL

  • Structured Query Language, criada na IBM nos anos 1970.
  • Padronizada pela ISO: o núcleo vale para todos os SGBDs.
  • Cada fabricante acrescenta extensões: T-SQL (SQL Server), PL/SQL (Oracle), PL/pgSQL (PostgreSQL).
  • É declarativa: diz-se o que se quer, não como buscar.

DBeaver: o cliente gráfico

  4. Alt+X executa o script inteiro.
  5. O resultado aparece na grade abaixo do editor.

Relacionamento: a ligação entre entidades

Associação entre ocorrências: Ana pertence à 3A. No DER, losango com um verbo, lido nos dois sentidos.

Ocorrências de um relacionamento

Papéis no relacionamento

  • O papel diz qual função a entidade cumpre no relacionamento.
  • PESSOA orienta PESSOA: um é orientador, outro é orientado.
  • Em TIME joga PARTIDA, um time é mandante e outro visitante.

Papéis aparecem escritos junto às linhas do DER quando a mesma entidade participa duas vezes.

Atributos do relacionamento

  • Alguns dados não pertencem a nenhuma das entidades, e sim à ligação.
  • ALUNO cursa DISCIPLINA: a nota é do par aluno-disciplina.
  • PRODUTO está em VENDA: a quantidade e o preço praticado são da ligação.

Cardinalidade: quantos com quantos

  • Diz com quantas ocorrências de uma entidade cada ocorrência da outra se associa.
  • Tem mínimo e máximo: (0,1), (1,1), (0,n), (1,n).
  • Mínimo 0: participação opcional. Mínimo 1: obrigatória.
  • Máximo 1 ou n: decide a forma das tabelas.
NotaçãoLeitura
(0,1)nenhum ou um
(1,1)exatamente um
(0,n)nenhum ou vários
(1,n)um ou vários

As três cardinalidades máximas

1:1

Cada pessoa tem um CPF; cada CPF é de uma pessoa.

1:N

Uma turma tem vários alunos; cada aluno, uma turma.

N:M

Um aluno cursa várias disciplinas; cada disciplina tem vários alunos.

Simulador de cardinalidade

Mude mínimo e máximo de cada lado. Observe a frase e o que o modelo lógico vai precisar.

Onde se escreve a cardinalidade: Chen e Heuser

  • Na notação de Peter Chen original, o número aparece junto à linha do lado oposto.
  • Na de Heuser (a do brModelo e desta unidade), a cardinalidade fica junto da entidade que está sendo contada.
  • Ex.: (1,1) junto de TURMA = cada aluno pertence a exatamente uma turma.
  • Sempre declarar no trabalho qual notação foi usada.

Regra de leitura (Heuser): parto de uma entidade, passo pelo losango e leio a cardinalidade que está do outro lado.

Lendo cardinalidades

RelacionamentoCardinalidadesLeitura

Cardinalidade é regra de negócio

  • Quem define é o minimundo, não o gosto do projetista.

  • “Uma turma pode existir antes de ter alunos”: mínimo 0.

Chave natural ou artificial?

Natural

Já existe no mundo real: CPF, placa, ISBN. Tem significado, mas pode mudar ou ter formato complicado.

Artificial (surrogate)

Duas ou mais colunas juntas: (aluno, disciplina) na tabela de notas.

Chave estrangeira (FK)

  • Coluna que guarda o valor da chave primária de outra tabela.
  • É ela que liga as tabelas: o “losango” do DER no modelo lógico.
  • Garante que não existam relações inválidas (aluno numa turma inexistente).

Integridade referencial

  • O SGBD recusa uma FK que não existe na tabela referenciada.
  • Também impede apagar uma turma que ainda tem alunos (por padrão).
  • Opções ao apagar o pai: RESTRICT (padrão), CASCADE, SET NULL.

Mapeando 1:N: a FK vai para o lado N

  • Cada aluno tem uma turma: cabe uma coluna turma em ALUNO.
  • Cada turma tem vários alunos: não cabe uma coluna em TURMA.
  • Mínimo 1 do lado de TURMA → NOT NULL.

Mapeando N:M: tabela associativa

  • Nenhum dos lados comporta uma só FK.
  • Cria-se uma terceira tabela com as duas FKs.
  • A PK é composta pelas duas FKs.
  • Atributos do relacionamento (nota, quantidade) ficam nela.

Mapeando 1:1

  • FK em um dos lados, com UNIQUE.
  • De preferência no lado com participação obrigatória.
  • Se as duas entidades sempre existem juntas, podem virar uma só tabela.

As propriedades ACID

Atomicidade

Tudo ou nada: uma falha desfaz a transação inteira.

Consistência

A transação leva o banco de um estado válido a outro: restrições respeitadas.

Isolamento

Transações simultâneas não enxergam o trabalho incompleto umas das outras.

Durabilidade

Depois do COMMIT, o dado sobrevive a quedas de energia.

ComandoFaz
BEGINabre a transação
COMMITconfirma tudo
ROLLBACKdesfaz tudo

  • Sem BEGIN, cada comando é confirmado sozinho (autocommit).

Transação como rede de segurança

Antes de um UPDATE ou DELETE grande: BEGIN, comando, SELECT para conferir, e só então COMMIT ou ROLLBACK.

Erro dentro da transação

  • Depois de um erro, o PostgreSQL recusa novos comandos até o ROLLBACK.
  • O COMMIT de uma transação com erro desfaz tudo: atomicidade.

Isolamento na prática

  1. Abrir duas conexões no DBeaver (A e B), modo de transação manual.
  2. Em A: BEGIN; UPDATE aluno SET cidade = 'Lavras' WHERE matricula = 2026001;
  3. Em B: SELECT cidade FROM aluno WHERE matricula = 2026001; → ainda Varginha.
  4. Em A: COMMIT; e repetir em B → Lavras.

O trabalho de A só fica visível para B depois do COMMIT.

Questão de modelagem 1

“Uma clínica veterinária registra tutores e animais. Cada animal pertence a um único tutor; um tutor pode ter vários animais. No modelo lógico, a chave estrangeira deve ficar:”

  • a) na tabela tutor, referenciando animal.
  • b) na tabela animal, referenciando tutor.
  • c) em uma tabela associativa tutor_animal.
  • d) nas duas tabelas.

Resolver antes de virar o slide.

Resolução comentada 1

  • Relacionamento 1:N: a FK fica no lado N, a tabela animal.
  • Alternativa correta: b.
  • c) seria para N:M; d) criaria redundância.

Questão de normalização

  • “Com chave (pedido, produto), a coluna cidade_cliente fere qual forma normal, e por quê?”
  • a) 1FN, por ter valores repetidos.
  • b) 2FN, por depender só de parte da chave (pedido → cliente → cidade).
  • c) 3FN apenas.

Resolução comentada 2

Questão de SQL 1

  • “A consulta devolve:”
  • a) todas as cidades dos alunos.
  • b) as cidades com mais de um aluno da T1 e a quantidade.
  • c) os alunos da T1.
  • d) um erro, pois HAVING exige ORDER BY.

Resolução comentada 3

WHERE filtra a T1, GROUP BY agrupa por cidade, HAVING mantém os grupos com mais de um. Alternativa b.

Questão de SQL 2

“Um técnico executou UPDATE produto SET preco = preco * 1.1; querendo reajustar só a categoria ‘cabos’. O que aconteceu e como evitar?”

  • a) Nada: falta COMMIT.
  • b) Todos os produtos foram reajustados; usar WHERE e testar com SELECT antes.
  • c) Erro de sintaxe.
  • d) Só o primeiro produto mudou.

Resolução comentada 4

  • Sem WHERE, o UPDATE vale para todas as linhas: alternativa b.
  • Em autocommit, já foi gravado; com BEGIN, um ROLLBACK desfaria.
  • Comando correto: UPDATE produto SET preco = preco * 1.1 WHERE categoria = 'cabos';
Interação

Simulado rápido

  • Ler a situação, identificar o conteúdo, eliminar o impossível.
  • Temas mais cobrados: FK no lado N, formas normais, GROUP BY/HAVING, WHERE em UPDATE.
  • Revisão geral no próximo encontro.
